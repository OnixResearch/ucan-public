## Context

`TimeBounds::new` is a pure `const fn` in `ucan-core`. It returns `InvalidTimeBounds` when the lower bound is not strictly earlier than the expiry and otherwise stores the two input values. The two getters return those stored values. This is a narrow but real runtime boundary and avoids the external string/serde/crypto models that would make a first downstream Aeneas pilot ambiguous.

The change depends conceptually on Octet's provider execution contract and Valence's translation-chain identity profile. Those repositories remain the execution and evidence-semantics authorities; UCAN owns only its source selection, theorem intent, local receipt, and documentation.

## Decisions

### 1. Target exact `ucan-core` source

**Choice:** The proof rail binds the constructor and getters defined in `crates/ucan-core/src/token.rs`. It may use a provider-owned selection manifest or wrapper only to select those exact compiled items. Supported selection requires reviewed non-errorful effective Charon options, exact target metadata, and measured `translation.json` rows linking each selected LLBC item to generated Lean declarations/files. Manifest `def_id` values are current-run joins only. The rail may not prove a copied or behaviorally similar shadow implementation.

**Rationale:** A copied constructor would add an unproved correspondence gap and would not strengthen the runtime boundary.

### 2. Keep the first downstream theorem finite

**Choice:** The maintained Lean theorem layer checks:

- `TimeBounds::new(nbf, exp)` is successful if and only if `nbf < exp`;
- equality and reversed order return the typed `InvalidTimeBounds` result carrying the original values; and
- successful results preserve `nbf` and `exp` through the getters.

The theorem map records exact Rust integer types, Aeneas-generated types, error representation, approved theorem-statement BLAKE3 identities, requirement IDs, claim classes, complete trust closure, theorem symbols, and source/model identities.

**Rationale:** These properties are directly reviewable and do not depend on ambient time or token orchestration.

### 3. Gate implementation on provider evidence

**Choice:** UCAN does not vendor or package the Aeneas toolchain. The proof rail selects an exact reviewed Octet provider revision/profile, effective extraction contract, theorem-adequacy policy, and compatibility receipt. Property evidence is accepted only after Octet artifact verification and Valence translation-chain validation agree on the source, extraction contract, LLBC, translation manifest, generated files, theorem approval/adequacy/trust closure, receipt, roles, and non-claims.

**Rationale:** Local proof intent does not justify duplicating stack execution or evidence semantics.

### 4. Exact-source failure is a valid blocked result

**Choice:** If Charon/Aeneas cannot translate the `const fn`, `Result`, error enum, struct construction, or getters under the reviewed provider, UCAN records a deterministic blocked receipt with stage, tool identities, bounded diagnostics, unsupported construct, and next smallest check. It does not remove `const`, rewrite the error type, or add a simplified proof-only implementation in this change.

**Rationale:** Changing the target to make the tool pass would stop proving the exact production core.

### 5. Separate generated definitions and theorem source

**Choice:** Generated Lean output is an explicit regenerable artifact. Hand-maintained theorem source imports it from a separate path. Freshness validation binds exact Rust source, effective extraction contract, LLBC, measured `translation.json`, generated-file inventory, Aeneas argv, generated bytes, theorem bytes, and Lean package/toolchain before a receipt can pass.

**Rationale:** Generated-model freshness and theorem maintenance are independent review surfaces.

### 6. Negative evidence is mandatory

**Choice:** Runtime tests cover accepted and rejected boundary values. When exact-source feasibility is supported, the proof rail includes an intentionally false theorem that must fail under the exact Lean toolchain and a vacuous `True` theorem that may check in Lean but must fail adequacy admission. Supported and blocked outcomes retain the applicable tamper inventory for errorful extraction, `skip_borrowck`, target/profile drift, source changes, stale LLBC, stale or mismatched `translation.json`, cross-run `def_id` reuse, stale generated Lean, wrong theorem/statement/requirement/claim identity, changed or undeclared trust inputs, wrong provider/Valence receipt, absent artifact verification, and overclaim text; theorem-stage cases remain gated until an exact generated model exists.

**Rationale:** A first consumer pilot must demonstrate fail-closed behavior before its receipt can influence readiness documentation.

### 7. Proof campaign resources are explicit and bounded

**Choice:** UCAN selects named Octet provider execution, log, and retained-artifact budgets and records their identities and outcomes. Exhaustion is a budget failure, not evidence that the Rust surface is unsupported or that a theorem is false. Blocked and counterexample outcomes remain first-class results.

**Rationale:** Repeatable proof campaigns need bounded resources and honest terminal outcomes without coupling those limits to runtime behavior.

### 8. Proof tooling stays outside runtime and support profiles

**Choice:** The proof runs only in explicit development/CI evidence lanes. `ucan-core` remains `no_std` and pure. Runtime issue/parse/verify/invocation APIs do not discover proof profiles or load receipts. Passing proof evidence does not promote protocol feature support levels in the integration support catalog.

**Rationale:** Verification evidence is not runtime policy, backend authority, or a new UCAN feature.

### 9. Broader UCAN adoption requires a later Cairn

**Choice:** Capability parsing, token claims construction, caveat validation, proof traversal, revocation, replay, signature handling, and authorization are excluded. Expansion requires reviewing model burden and selecting a new exact source/property pair.

**Rationale:** A constructor microproof does not establish that string-heavy, allocation-heavy, cryptographic, or orchestration surfaces fit Aeneas.

## Risks / Trade-offs

- Aeneas may not support the exact `const fn` or error representation. The blocked result remains useful feasibility evidence but provides no proof claim.
- The theorem can prove the constructor while callers still misuse timestamps or ambient clocks. Those behaviors remain outside scope.
- Existing verified-logic predicates may overlap conceptually. The theorem map must describe complementary exact-runtime evidence rather than claim replacement or transfer.
- Toolchain and generated-artifact maintenance adds CI cost. The rail remains opt-in and bounded to one source selection and named budget profile.
- Aeneas `def_id` values can change across runs. UCAN preserves them only as frozen manifest links and never as source, theorem, or receipt identity.
